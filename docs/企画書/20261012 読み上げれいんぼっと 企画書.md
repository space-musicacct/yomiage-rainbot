## 2. 前提

本企画書は、Discord サーバー「[びすこーど！](https://biscord.bistan-tool.com/)」専用の読み上げ Bot「読み上げれいんぼっと」を開発する背景・目的・基本方針を整理するものである。

開発対象となるシステムの機能要件・非機能要件・スコープは、要件定義書で扱う。

## 3. 背景

### 3.1 びすこーど！の読み上げ Bot の利用状況

びすこーど！では、「VOICEROID 読み上げbot」「VOICEVOX読み上げbot」(この 2 つは同一の運用元) など複数の読み上げ Bot を導入しているが、**主に利用されているのは「ずんだもんβ」** である。

### 3.2 発生した事象

びすこーど！で、複数の利用者の読み上げ音声が意図せず変わる現象が報告された。利用者側で `/setvc` を実行すれば元に戻せることは確認済みである。

**本番環境における根本原因は未確定**である。3.3 の調査で見つかった既存実装の問題点と、当該事象の原因は区別して扱う。

### 3.3 既存 Bot の公開実装の調査

ずんだもんβの公開実装である [lenlino/DiscordVoiceVox](https://github.com/lenlino/DiscordVoiceVox) (MIT License) を静的に調査した。本節は 2026-10-12 時点の調査内容である。

調査対象は [コミット `9b1a3ce`](https://github.com/lenlino/DiscordVoiceVox/tree/9b1a3cead9a35543bb05b1d3be709128337f57ca) 時点の公開コードである。**本番環境で利用中のコミット・DB の実スキーマ・実行ログは未確認**であり、以下はいずれも 3.2 の事象の根本原因と断定するものではない。

#### A. 設定データの整合性に関わる問題

##### P-001 JSONB コーデックの接続ごとの不一致、および二重シリアライズの危険性

`initdatabase()` 内で、プールから取得した 1 接続だけに `set_type_codec("jsonb", encoder=json.dumps, decoder=json.loads)` を設定しており、プールの全接続に登録する処理になっていない ([初期化](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L552-L555))。

一方、`setdatabase()` は `auto_join` / `member_voices` を `json.dumps` してから DB ドライバに渡している ([DB 処理](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L2698-L2779))。コーデック設定済みの接続では再び `json.dumps` され、DB に JSON オブジェクトではなく JSON 文字列が保存され得る。

読み出し側の型・保存済みデータの形によって `member_voices` が `dict` として得られない経路があり、その場合はサーバー別の音声設定が適用されない ([読み上げ側](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L3240-L3252))。設定の読み出し結果が、接続や保存状態に左右されるリスクがある。

##### P-002 主キー・一意制約がテーブル作成定義にない

`voice(id char(20), voiceid char(4))` および `guild(id char(20), ...)` に `PRIMARY KEY` / `UNIQUE` がない ([スキーマ定義](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L553-L565))。

`getdatabase()` / `fetch_row()` は行の存在を確認してから `INSERT` し、`setdatabase()` も `SELECT → INSERT → UPDATE` を行うが、これらのチェックと更新は単一の原子的操作ではない ([DB 処理](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L2713-L2780))。並行アクセス時に、重複レコード・競合・予期しない設定参照が起こり得る。なお、本番 DB で別途制約が追加されている可能性は否定できない。

##### P-003 音声 ID の固定長制限

`voice.voiceid` は `char(4)` である ([スキーマ定義](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L553-L557))。5 文字以上の音声 ID を格納する仕様へ拡張した場合は対応できない。現在のサービスで該当 ID が使われたという確認ではなく、コード上の制限として扱う。

#### B. 特定の入力・実行経路で確認できる不具合

##### P-004 一時音声ファイル名の生成で未定義のグローバル変数を参照

`get_temp_name()` は `global counter; counter += 1` を実行するが、初期化されているのは `bot.counter = 0` であり、モジュール変数 `counter` の初期化は確認できない ([関数](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L2920-L2925))。当該関数はファイル出力などで実際に呼び出される ([使用箇所の例](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L3544-L3552)) ため、該当経路を通ると `NameError` が発生し得る。

##### P-005 DM 受信時の `None` 参照

`on_message()` 冒頭で `message.guild.voice_client` を無条件に参照している ([該当箇所](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L3063-L3067))。Discord の DM では `message.guild` が `None` となるため、DM を受信した場合は `AttributeError` となる経路がある。

##### P-006 添付ファイルがあると `!` / `！` による読み上げ抑止が効かない

`on_message()` が本文の先頭に `テンプファイル` を付加し ([該当箇所](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L3064-L3070))、後段で加工後の文字列に対して `startswith("!")` / `startswith("！")` を判定している ([該当箇所](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L3148-L3154))。元の本文が `！あいうえお` でも、添付時は先頭が `テンプファイル` になり、抑止判定をすり抜ける。

具体的な再現手順をspaceが [Issue #202](https://github.com/lenlino/DiscordVoiceVox/issues/202) においても報告している。

**追記 (2026-10-17):** 本件は 2026-10-14 の [コミット `d0f0686`](https://github.com/lenlino/DiscordVoiceVox/commit/d0f06867383a0666925cb2765566960f1b25c503) で修正され、Issue #202 はクローズされた。ずんだもんβにおいても解消されたことを space が確認した。

##### P-007 Lavalink 向けのクエリ分割で読み上げ文字列が壊れ得る

[`LavalinkClient.py`](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/LavalinkClient.py) の `Playable.search()` は、`usegpu` クエリを `query.split("_")` で分割し、`parts[4]` だけを本文として使用する。本文にアンダースコア `_` が含まれると、それ以降のテキストが欠落し得る。該当経路の利用が前提の不具合である。

#### C. 構造的な保守性の問題

##### P-008 責務の集中

`main.py` は約 4,800 行にわたり、Discord イベント、コマンド、DB スキーマ初期化、DB CRUD、音声合成、読み上げ制御、外部サービス連携等の責務が集中している。

##### P-009 グローバル変数と `bot.*` の状態管理の混在

グローバル変数と `bot.*` の状態管理が混在している。例えば `voice_id_list = bot.voice_id_list` と別名参照した後に `voice_id_list = json` と再代入しており、両者の参照先が一致しなくなる ([初期状態](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L214-L246)、[再代入](https://github.com/lenlino/DiscordVoiceVox/blob/9b1a3cead9a35543bb05b1d3be709128337f57ca/main.py#L690-L696))。それだけで実害の発生とは断定しないが、状態の追跡を難しくする。

### 3.4 調査上の結論

既存の公開コードには、実行時例外に直結する経路と、設定の整合性に影響し得る実装上の欠陥が複数ある。一方、本番環境の障害原因と全利用者への影響範囲は未確認である。

規模に対して原因調査と保守に要する工数が大きいため、単発の修正ではなく、責務分離・DB 制約・設定の優先順位・テスト容易性を最初から設計し直す。

## 4. 企画の目的

### 4.1 目的

びすこーど！で利用する音声読み上げ Bot を、既存 Bot の構成をそのまま引き継ぐのではなく、設計から見直して独立開発する。

最初はびすこーど！専用 Bot として開発・運用し、実利用者への安定提供を優先する。

### 4.2 目指す状態

| ID    | 目指す状態                                               |
| ----- | -------------------------------------------------------- |
| G-001 | びすこーど！の利用者に、安定した読み上げを提供できる     |
| G-002 | 3.3 で確認した種類の問題を、設計と回帰テストで予防できる |
| G-003 | 不具合が起きた時に、原因を調査しやすい構造になっている   |

## 5. 基本方針

### 5.1 責務を分離する

Python で実装し、オブジェクト指向を活用して責務を分離する。既存の巨大な単一ファイル構造は踏襲しない。

### 5.2 大型フレームワークの導入は慎重に判断する

Discord 向けライブラリは活用するが、Bot 本体のイベントループやライフサイクルと競合し得る汎用アプリケーションフレームワークの導入は慎重に判断する。

### 5.3 音声データはファイルシステムで扱う

音声データ本体は原則ファイルシステムで扱い、永続管理が必要なものは DB にメタデータ・保存パスを紐付ける。Docker を利用する場合は、コンテナ内の保存パスを固定し、ホスト側の配置をマウントで調整する。

### 5.4 公開と正式リリースを区別する

開発開始時点から本リポジトリを Public で開発する。README 冒頭には、未完成・開発中 (WIP) であること、機能・仕様・DB 構造が変更され得ること、現段階では動作・安定性を保証しないことを明示する。

Public は開発状況の公開を意味し、完成・品質保証・正式リリースや一般向け Bot ホスティングの開始を意味しない。品質保証を一定水準まで確保してから正式リリースする。また、ソースコードの公開と、Bot を第三者向けにホストして一般提供することは別の事項とする。

### 5.5 既存コードのライセンスを遵守する

既存コードを再利用する場合は、MIT License の著作権表示・許諾表示など、適用されるライセンス条件を遵守する。

## 6. 進め方

### 6.1 開発方式の比較

| 案  | 内容                                                             | 判断   |
| --- | ---------------------------------------------------------------- | ------ |
| A   | 既存リポジトリを fork し、不具合を個別に修正する                 | 不採用 |
| B   | 新しい構成で独立開発し、既存コードは必要な部分を改変して取り込む | 採用   |

案 A は、P-008 / P-009 の構造のまま単発の修正を重ねることになり、原因調査と保守の工数が減らない。案 B は、責務分離・DB 制約・テスト容易性を最初から設計でき、既存の実装資産も活用できる。

案 B では既存コードを少なくとも改変して利用することになるため、LICENSE に lenlino 氏と space の著作権表示を併記し、README にクレジットを記載する (5.5)。

### 9.1 Q-001 で MySQL 8.4 を第一候補とする理由

既存の MySQL 8.4 の運用経験・環境を活用できること、主な永続データが Bot の設定・辞書・音声ファイルのメタデータ等であり、現時点で PostgreSQL 固有機能を要求する要件が見当たらないこと、MySQL でも Alembic 等によるマイグレーション管理と必要な `ALTER TABLE` に対応できることが理由である。

ローカル / テスト環境での事前検証、必要時の本番相当データによる移行テスト、本番適用前のメンテナンス告知・ダンプ取得を想定しており、PostgreSQL の Transactional DDL だけでは採用を変更する決定的理由にならない。要件の変化によって PostgreSQL を再評価する余地は残す。
