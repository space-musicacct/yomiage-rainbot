# VC 接続管理と状態管理の設計メモ

- 検討日： 2026-10-17
- 対象： VC 接続管理・状態管理・デザインパターンの活用

---

## 1. 背景

読み上げれいんぼっとの開発に先立ち、びすこーど！の利用者から既存 Bot の機能継承に関する意見を募集した。

その中で、読み上げ途中に別の利用者の音声へ切り替わる挙動について、継承希望が寄せられた。

本件を検討する過程で、以下の設計案が浮上した。

1. VC 接続単位での状態管理

## 2. VC 接続単位の状態管理

### 2.1 基本方針

VC 接続ごとに独立したオブジェクトを生成し、その接続固有の状態をインスタンスメンバとして管理する。

これにより、異なる接続間で状態が意図せず共有されることを防ぐ。

### 2.2 Voice Override Mode (仮称)

利用者から要望のあった音声切り替え挙動について、仮に実装する場合は、VC 接続単位で ON/OFF を制御する方式を検討する。

想定コマンド：

`/voice-override-mode`

想定仕様：

- デフォルトは OFF
- VC 接続単位で有効・無効を管理
- VC 切断時に設定を破棄
- DB への永続化は原則不要
- 通常の音声設定とは独立して管理

Python では、例えば次のように管理できる。

```py
class VoiceSession:
    def __init__(self):
        self.voice_override_mode: bool = False
```

※ 上記は状態管理の概念例であり、音声切り替え処理そのものの実装ではない。

### 2.3 永続化を不要とする理由

設定の有効期間が VC 接続中に限定されるのであれば、接続オブジェクトのライフサイクルと設定のライフサイクルを一致させられる。

接続終了時にインスタンスを破棄すれば、状態も破棄できる。

永続化を必要とする新たな要件がなければ、DB に保存する合理性は乏しい。

## 3. 複数 VC 接続の管理

### 3.1 検討対象

異なる VC への Bot の Join 要求について、接続先の選択・解決および接続処理を統一的に管理する仕組みを設計する。

接続要求の順序制御には `asyncio.Queue` などを利用できるが、Queue だけに管理責務を集中させる必要はない。

### 3.2 デザインパターンの活用

以下の 3 パターンの組み合わせを検討する。

| パターン | 想定する責務                                     |
| -------- | ------------------------------------------------ |
| Facade   | Join 要求などを受け付ける統一インターフェース   |
| Adapter  | 実際の接続先の選択・解決と、接続手段の差異の吸収 |
| Strategy | 接続要求を処理する方針・アルゴリズムの切り替え  |

構成イメージ：

```text
Discord Command / Event
          |
          v
   VoiceConnectionFacade
          |
          +-- ConnectionAdapter
          |     └─ 接続先の選択・解決
          |
          +-- ConnectionStrategy
          |     └─ 接続処理方針の決定
          |
          +-- VoiceSession
                └─ 接続固有の状態
```

※ 依存関係や呼び出し順序は未確定。上図は責務分担の概念図である。

### 3.3 期待する効果

- 呼び出し側が個別の接続実装を意識せずに済む
- 接続先の選択ロジックを局所化できる
- 接続方針の変更による影響を限定できる
- VC 接続ごとの状態を独立して管理できる
- 接続管理機構の単体テストを実施しやすくなる

## 4. Python の多重継承の活用

Python は多重継承をサポートしている。

この言語特性を活用すれば、必要に応じて複数クラスの機能を組み合わせた設計が可能となる。

特に Mixin による横断的な機能の提供が候補となる。

例えば、ログ記録やリトライ処理などを独立した Mixin として構成する方法が考えられる。

ただし、以下を考慮する。

- MRO (Method Resolution Order) と C3 線形化
- `super()` を利用する場合の協調的多重継承
- 各クラスの責務とメソッドシグネチャの整合性
- 継承とコンポジションの使い分け

Facade・Adapter・Strategy のすべてを多重継承で実現する必要はない。

実行時に変更する Strategy などにはコンポジションが適する場合もある。

多重継承は採用自体を目的とせず、責務を適切に組み合わせる手段として活用する。

## 5. 設計上の重要な考え方

### 5.1 状態と責務の所属を明確にする

VC 接続固有の情報は接続オブジェクトに、接続先の解決は Adapter に、接続処理方針は Strategy に分離する。

### 5.2 過度な抽象化を避ける

今回の抽象化案は、実際に異なる責務として認識できる処理を分離することを目的としている。

ただし、各パターンの具体的なクラス数・階層・インターフェースは、要件定義後に必要性を評価して決定する。

### 5.3 接続と状態のライフサイクルを一致させる

接続固有の一時的な状態については、接続オブジェクトとともに生成・破棄する設計を基本候補とする。

### 5.4 設定の永続化は要件に基づいて判断する

DB に保存できることと、保存する必要があることは別である。

接続中だけ有効な設定を永続化しないことで、不要な DB 操作や状態管理を削減できる。

これにより、複数 VC の接続管理、接続先の解決、接続固有の状態管理を、それぞれの責務に応じて整理できる可能性がある。
